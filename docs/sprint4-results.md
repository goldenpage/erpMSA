# 4차 스프린트 검증 결과

> 아래 수치는 실험 당시의 기존 구현에 대한 기록이다. 목표 서비스 구조는
> [서비스 설계 기준](service-architecture.md)을 따르며 새 도메인 서비스의 검증 결과로 인용하지 않는다.

기존 인증·품목·재고·감사 흐름에서 서명 권한을 분리하고, 품목 목록의 SQL 비용과 장애 영향을 검증했다.
신규 OrderService는 추가하지 않았다. 변경은 로컬 작업 트리에 있으며 원격 Jenkins 재실행·운영 배포는 하지 않았다.

## 구현

- JWT HS256 공통 비밀키를 RS256으로 교체했다. Account만 개인키를 받고 Gateway·Item·Inventory는 공개키 묶음으로 검증한다.
- 키 ID, 허용 알고리즘, issuer/audience, 토큰 종류와 만료를 검증한다. 키 교체는 공개키 선배포 → 서명키 전환 → 구키 만료 후 제거 순서다. 원격 JWKS 자동 갱신은 구현하지 않았다.
- 최초 전환 시 기존 HS256 토큰은 거절된다. 재로그인이 필요하며 Refresh 14일을 포함한 정상 키 교체 절차는 [설계 결정](sprint4-design.md)에 있다.
- 품목 목록에 `(account_id,status,created_at,id)` 인덱스와 동일 생성 시각의 `id DESC` 정렬 기준을 추가했다.
- Kafka 이벤트 계약, 선택 필드 호환성, 중복 방지, 잘못된 payload의 DLT 처리를 검증하도록 보완했다.
- 인스턴스별 Prometheus 수집과 Outbox 적체·나이, DB 연결 대기, GC 진단 대시보드를 추가했다.

## 부하 설계와 해석

실제 검색·홈 API가 없으므로 존재하는 `GET /items`를 선정했다. 계정 필터, 상태, 정렬, 깊은 페이지와 count 비용을
관측할 수 있는 경로다. 운영 트래픽 로그가 없으므로 아래 요청 분포는 가설이며 실사용 대표값이라고 주장하지 않는다.

Docker Desktop 단일 VM(12 CPU, 약 7.75 GiB)에서 계정 6개, 품목 21만 개를 생성했다.
최종 검증의 Docker Engine은 29.7.2였으며 비교한 여섯 HTTP 실행의 workload·dataset SHA-256은 각각 동일했다.
계정별 1만/1만/2만/2만/5만/10만 건, ACTIVE 80%, 설명 200바이트다.
요청은 ACTIVE/INACTIVE/상태 없음 약 60/20/20%, 페이지 크기 20/50/100, 약 65%가 첫 세 페이지다.
나머지는 유효한 뒤쪽 페이지를 선택한다. 동일 iteration의 파라미터는 결정적 해시로 재현한다.

Item/Gateway 각각 1 CPU·512 MiB, DB 2 CPU·1536 MiB, k6 1 CPU·512 MiB다.
k6는 150 VU를 미리 할당하고 초당 80회, 60초간 요청한다. 측정 중 빌드·서비스 테스트를 병행하지 않았다.
오류율과 `dropped_iterations`를 함께 기록했다. 자세한 원시 통계의 공유용 추출본은
[sprint4-measurements.json](sprint4-measurements.json), 재현 명령은 [실험 안내](../performance/README.md)에 있다.

### 인덱스 전후

2026-09-13 실험은 같은 애플리케이션 이미지에서 임시 DB의 인덱스 하나만 변경했다.
당시 API는 `createdAt DESC` 정렬이었고 seed의 생성 시각은 유일했다. 최종 코드에는 동일 시각의 순서 보장을 위한
`id DESC`도 추가했으며 최종 이미지에서 별도로 측정한다. 기준 Git HEAD는 `dd3c81e4c4e97f782d66fe4f511f895253c011ed`이며,
실험 이미지는 그 위의 RS256 작업 트리 변경을 포함하므로 HEAD 자체를 실행한 수치가 아니다.

| 경로 | 인덱스 전 평균 / p95 | 인덱스 후 평균 / p95 | HTTP 오류 / 누락 |
|---|---:|---:|---:|
| Gateway 경유 | 8.67 / 28.81 ms | 7.64 / 24.07 ms | 모두 0 / 0 |
| Item 직접 | 8.00 / 29.07 ms | 6.88 / 22.83 ms | 모두 0 / 0 |

각 실행은 4,800~4,801건이다. Gateway p95는 이 표본에서 약 16.5% 낮아졌다.
한 번의 60초 측정으로 운영 개선율을 확정할 수 없다. Gateway/직접 호출이 비슷하다는 관측 역시
이 요청률에서 Gateway가 주된 지연 원인이라는 증거가 없다는 뜻이며 최대 처리량 검증은 아니다.

SQL은 10만 건 계정의 `INACTIVE`, page=100, size=20에서 개선 원인이 더 명확했다.

| 관측 | 전 | 후 |
|---|---:|---:|
| 실제 읽은 행 | 10,100 | 2,020 |
| 접근한 엔진 페이지(첫 표본) | 30,326 | 6,068 |
| SQL 실행 시간 중앙값(5회) | 5.514 ms | 1.322 ms |
| 선택 인덱스 | account_created | account_status_created |

상태를 인덱스에서 먼저 좁혀 불필요한 행 탐색이 줄었다. 해당 SQL의 시간 감소는 약 76%다.
ACTIVE 첫 페이지나 전체 건수 조회까지 같은 비율로 빨라진 것은 아니다. count 비용은 남으며,
깊은 offset 자체를 없애려면 페이지 계약·커서 페이지네이션을 별도로 검토해야 한다.
추가 인덱스의 저장공간과 쓰기 비용은 이번 읽기 부하 실험에서 측정하지 않았다.

초기 탐색 실행 `baseline-gateway`는 30 VU 선할당으로 요청 93건이 누락되어 위 비교에서 제외했다.
콜드스타트·JIT 등도 분리하지 않았으므로 당시 지연과 이후 지연의 차이를 VU 설정 효과로 단정하지 않는다.

## 검증 범위와 남은 일

### 최종 이미지 증설 비교

2026-09-15 전용 관측 볼륨과 다시 생성한 동일한 21만 건 데이터로 측정했다.
Item 이미지·인덱스·요청 분포는 같고 Item 인스턴스 수만 1개에서 2개로 늘렸다.

| Item 수 | 요청 수 | 평균 | p95 | p99 | 오류 / 누락 |
|---|---:|---:|---:|---:|---:|
| 1 | 4,801 | 8.38 ms | 23.89 ms | 57.10 ms | 0 / 0 |
| 2 | 4,801 | 8.19 ms | 23.71 ms | 58.08 ms | 0 / 0 |

두 인스턴스의 측정 종료 시점 1분 rate는 각각 약 40.09/40.07 RPS였다(HTTP 서버 메트릭 기준).
분배는 확인했지만 p95 차이는 약 0.18ms로 작고 p99는 오히려 조금 증가했다.
80 RPS에서 증설의 성능 효과를 주장할 근거는 부족하다. 자원 포화 조건과 반복 측정을 먼저 확보해야 한다.

### 자동 검증

서비스 자동 테스트는 Account 35, Item 16, Inventory 21, Gateway 15, Audit 4개로 총 91개가 통과했다.
CI 키 전달을 모사한 임시 볼륨 실험에서 비루트 사용자 읽기 권한과 서명/검증 키 분리도 확인했다.
Jenkinsfile의 회전된 Refresh 쿠키 저장 및 로그아웃 후 재사용 401 검증을 수정했지만 원격 CI 전체 실행은 남아 있다.
실험 볼륨 보호 회귀 테스트 3개도 통과했다.

Refresh 회전 후 구토큰 401, 로그아웃 후 회전된 토큰 401, RSA 인증으로 Item→Inventory 호출,
계정 간 재고 조회 404를 확인했다. 같은 version의 재고 조정 10개를 동시에 요청해 1개 성공·9개 충돌을 관측했다.
수량은 20→19, 원장은 최초 입고와 조정 2개였고 동일 requestId 재사용은 409였다.
같은 eventId의 Kafka 이벤트를 두 번 추가 발행해도 감사 레코드는 1개였으며 잘못된 JSON은 DLT로 이동했다.

### 장애 주입

아래 요청은 약 0.2초 간격의 순차 목록 조회다. 요청별 최대 대기는 10초이므로 응답 지연 시 표본 수가 줄어든다.
부하 한계나 운영 가용성 SLO를 측정한 값이 아니다.

| 실험 | 관측 | 해석 |
|---|---|---|
| Eureka 중단 약 20초 | 목록 95건 모두 200 | 이미 발견한 인스턴스의 캐시 호출은 유지됐다. 신규 발견은 검증하지 않았다. |
| 안정화 후 Item 1개 SIGKILL, 약 30초 | 200 24건, HTTP 500 22건, 클라이언트 네트워크 예외 2건 | 살아 있는 replica로 모든 요청을 우회하지 못했다. 프로세스 장애 내성 보완이 필요하다. |
| Kafka 중단 약 20초 | 목록 94건 모두 200, 회원가입 201, Outbox PENDING 1건 | 요청 처리와 감사 발행이 분리됐다. |
| Kafka 재시작 | 약 9.69초 뒤 PENDING 0, Outbox 대비 누락 감사 레코드 0 | 해당 장애에서 이벤트를 잃지 않고 재처리했다. 브로커 HA의 증거는 아니다. |

Item 종료는 명시적 SIGKILL이며 Docker 상태는 `ExitCode=137`, `OOMKilled=false`였다.
수동 시작으로 복구했다. 종료 코드 137만으로 heap 부족이라고 결론 내리지 않았다.
Kafka 중단 중 Prometheus에서도 pending=1과 oldest age 증가를 관측했다.
DB가 복구된 직후의 scrape에는 이전 값이 남을 수 있어 수집 주기(15초)를 고려하고 안정화 후 다시 대조했다.

첫 Item 종료 실행은 Eureka 재시작 뒤에 수행했고, 144건 중 115건이 500이었다.
로그를 확인하니 `No servers available for service: ITEMSERVICE` 87건과 죽은 컨테이너 이름 조회 실패가 함께 있었다.
서버에 두 인스턴스가 UP이어도 Gateway 캐시는 아직 비어 있을 수 있었다. 이 실행은 복합 장애 표본으로 보존하고
단독 Item 장애 수치에 섞지 않았다. 이후 정상 경로가 연속 10회 응답하는 것을 확인한 뒤 위 단독 실험을 재실행했다.

Account 이미지 재배포 직후에도 이전 컨테이너 이름에 대한 `UnknownHostException`과 회원가입 500을 관측했다.
캐시 갱신 후 종단 검증은 통과했지만 무중단 재배포가 검증됐다는 의미는 아니다.
후속 우선순위는 (1) 읽기 요청의 제한적 실패 우회와 인스턴스 건강 확인,
(2) readiness·등록·기존 요청 drain을 포함한 배포 절차,
(3) 실제 트래픽/SLO 기반 반복 부하다. 특히 쓰기 요청에는 중복 실행을 막는 계약 없이 재시도를 추가하지 않는다.


### 미검증 범위

이번 환경은 단일 호스트·단일 Eureka·단일 Kafka 브로커다. 인스턴스 증설은 호스트 장애의 고가용성을 증명하지 않는다.
SIGKILL 실험은 JVM OOM 재현이 아니다. GC 로그·heap dump 옵션을 준비했어도 메모리 누수나 OOM 원인을
분석한 실적으로 쓰면 안 된다. 운영 SLO, 장시간 soak, 포화점, 다중 호스트 및 브로커 장애 내성은 후속 검증이다.

## 실험 도구 보완 이력

초기 overlay가 기본 Compose의 명시적 볼륨 이름을 상속하여 실험용 Prometheus·Grafana가
기존 `erpmsa-prometheus-data`, `erpmsa-grafana-data`에 연결됐다. 이 기간의 관측 데이터가 해당 볼륨에 기록됐으며,
기존 볼륨을 삭제하거나 임의로 복원하지 않았다. 업무 MariaDB·Redis·Kafka 데이터는 tmpfs로 분리했다.

후속 검토에서 모든 선언 볼륨을 `erpmsa-sprint4-lab-` 이름으로 바꾸고, 시작·정리 전에 비실험/외부 볼륨을
거절하는 검사와 회귀 테스트 3개를 추가했다. 인덱스 전후 표의 k6·SQL 결과는 해당 관측 볼륨에 의존하지 않는다.
분리 이후의 증설·장애 결과는 새 전용 관측 볼륨에서 수집한다.

최종 검증 후 실험 컨테이너·네트워크·전용 관측 볼륨을 정리했다. 기존 MariaDB·Redis·Kafka·Prometheus·Grafana
볼륨의 존재를 다시 확인했다. 원시 결과는 Git에서 제외한 `performance/results/`에 남겨 두었으며,
공유용 JSON에는 토큰·환경변수·개인키를 포함하지 않는다.
